# ea-kernel Purpose

## 목적

ea-kernel은 비즈니스 의사결정에 관여하는 엔티티와 그 관계를 프레임워크에 독립적으로 표준화하기 위한 정적 스펙 정의 레이어다.

## 배경

비즈니스에서 발생하는 의사결정은 항상 "무엇이(엔티티) 어떻게(관계) 연결되는가"의 구조를 갖는다. 이 구조를 ArchiMate, TOGAF, Zachman, SysML, BPMN 각각이 자기 어휘로 표현하지만, 의사결정 구조의 본질은 프레임워크와 무관하다.

프레임워크가 달라도 동일한 의사결정 구조를 비교할 수 있게 하는 것이 ea-kernel의 존재 이유다.

## 설계 원리

KerML의 "행위는 관계의 자격(qualification)" 원리에 기반한 4계층 점진적 추상화로 의사결정 구조의 본질을 포착한다.

| 계층 | 역할 | 의사결정 관점 |
|------|------|-------------|
| L1 Structure | 의사결정에 참여하는 것들 | "무엇이 있는가" |
| L2 Relationship | 그것들의 구조적 연결 | "어떻게 묶이는가" |
| L3 Behavioral | 연결에 행위 자격 부여 | "어떤 흐름/순서/상호작용이 가능한가" |
| L4 Concrete | 구체적 행위 모델 | "실제로 무엇이 일어나는가" |

L3는 L2와 별개의 세계가 아니라 L2의 자격부여이므로, 구조와 행위가 하나의 연속체로 표현된다.

## 커널의 범위

커널은 **토폴로지 거버넌스**를 담당한다: 어떤 엔티티가 어떤 관계로 연결될 수 있는지(고유 식별 + 유효성 규칙).

| 커널 안 | 커널 밖 |
|---------|---------|
| 타입 카탈로그 (15 entities × 14 relations) | Feature composition/typing 제약 (소비자 레이어 책임) |
| 유효성 규칙 (67 explicit + 14 fallback) | 인스턴스 (M0 — SQLite/TOML/TypeDB의 실제 데이터) |
| 프로파일 프레임워크 (도메인 매핑 + 수명주기) | 분석/시각화 (소비자 영역) |

**MOF 레이어링**:
- M3: `types.py` — 메타모델 정의 어휘 (KernelEntity, KernelRelation, KernelValidityRule, KernelSchema)
- M2: `definition.py` + `spec` — 15 entities × 14 relations × 67 rules
- M1: `profiles/*.py` + profile framework — 도메인 요소→커널 타입 매핑
- M0: 소비자 영역 — SQLite/TOML/TypeDB로 인스턴스 생성

## 커널이 가능하게 하는 것

1. **프레임워크 간 의사결정 구조 비교** — 15개 엔티티와 14개 관계라는 공통 어휘로 환원되므로, 프레임워크가 달라도 동일한 의사결정 구조를 비교할 수 있다.
2. **구조적 경계의 명시** — validity rule이 "이 조합은 구조적으로 불가능"을 선언한다. 프레임워크의 도메인 지식 없이도 구조 자체가 허용/금지하는 관계의 경계가 정의된다.
3. **보편 제약과 도메인 제약의 분리** — 커널은 보편적 구조 제약만 담당하고, 도메인 특화 제약은 프로파일이 추가한다. 프로파일은 커널 위에 제약만 추가할 수 있고, 완화할 수 없다.
4. **프로파일 수명주기 관리** — 프로파일의 직렬화(JSON round-trip), 영속화(SQLite), 버전 관리(version chain + tag), 구조적 diff, 내성(introspection), 합성(extend/subset)을 통해 프로파일이 코드에 하드코딩되지 않고 데이터로서 관리된다.
5. **AI 친화적 의사결정 기반** — 규칙 코퍼스를 통한 증거 기반 추론. 규칙의 출처·신뢰도·도메인을 메타데이터로 관리하여, AI 에이전트가 "왜 이 관계가 허용/금지되는가"를 구조화된 증거와 함께 판단할 수 있다.
