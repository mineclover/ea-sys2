# ea-kernel v1.2 Specification

v1.1 → v1.2 변경점. SysML 2.0 프로파일(13/13 커널 관계 스트레스 테스트)에서 발견된 개선점 반영.

## 발견 경위

v1.1에서 ArchiMate/TOGAF/Zachman 3개 프로파일은 13개 커널 관계 중 6개만 사용.
SysML 2.0 프로파일로 나머지 7개(feature_typing, connector, redefinition, subsetting,
interaction, triggering, guarding)를 전부 활성화한 결과, 커널 스펙의 구조적 결함이 드러남.

핵심 패턴: **프로파일이 커널의 과잉 허용을 deny 규칙으로 보상하는 반복이 발생**
→ 커널 수준에서 제약을 강화해야 프로파일 부담이 줄어듬.


## 1. 커널 스펙 규칙 보강 (spec.py)

### 1-A. Cross-layer deny 누락: expression (Critical)

**현상**: L4 엔티티 5개 중 4개(state, step, action, event)는 동종 association deny가 있지만
`expression`만 빠져있음.

```python
# 기존 (v1.1): cross-01~04만 존재
cross-01: state → state → association = DENY (p=90)
cross-02: step → step → association = DENY (p=90)
cross-03: action → action → association = DENY (p=90)
cross-04: event → event → association = DENY (p=90)
# expression → expression → association = ALLOWED (assoc-01, p=40) ← 버그
```

**수정**: `cross-05` 추가

```python
cross-05: expression → expression → association = DENY (p=90)
```

**검증**: `KERNEL_SPEC.validate_relationship("expression", "expression", "association")` → 현재 ALLOWED, v1.2에서 DENIED


### 1-B. 이종 L4-L4 association deny (High)

**현상**: 동종(same-type)만 deny하고, 이종(cross-type) L4 조합은 허용됨.

```
step → event → association = ALLOWED (assoc-01)   ← 의미 없음
state → expression → association = ALLOWED         ← 의미 없음
event → expression → association = ALLOWED         ← 의미 없음
```

L4 엔티티끼리의 association은 모두 의미론적으로 부적절:
- L4는 behavioral/concrete 계층이고, association은 L2 structural 관계
- 프로파일에서 이런 조합은 전혀 사용되지 않음 (4개 프로파일 기준)

**수정**: 전체 L4×L4 association deny

```python
cross-06: step* → state → association = DENY (p=90)
cross-07: step* → event → association = DENY (p=90)
cross-08: step* → expression → association = DENY (p=90)
cross-09: state → step* → association = DENY (p=90)
cross-10: state → event → association = DENY (p=90)
cross-11: state → expression → association = DENY (p=90)
cross-12: event → step* → association = DENY (p=90)
cross-13: event → state → association = DENY (p=90)
cross-14: event → expression → association = DENY (p=90)
cross-15: expression → step* → association = DENY (p=90)
cross-16: expression → state → association = DENY (p=90)
cross-17: expression → event → association = DENY (p=90)
```

**대안**: 단일 규칙으로 압축 가능한지 검토. 현재 패턴 매칭은 OR/AND 미지원이므로
개별 규칙이 필요. `L4*` 같은 새 패턴을 도입하면 2개 규칙으로 축소 가능:

```
L4* → L4* → association = DENY (p=90)  # 신규 패턴 필요
```

**결정 필요**: 12개 개별 규칙 vs `L4*` 패턴 도입


### 1-C. state ↔ feature specialization deny (Critical)

**현상**: `classifier ↔ feature` specialization은 deny(spec-04, spec-05)지만,
`state`는 `metatype` 직계 자식이라 이 deny를 회피함.

```
state → feature → specialization = ALLOWED (spec-01: metatype*→metatype*)  ← 의미 없음
feature → state → specialization = ALLOWED (spec-01)                       ← 의미 없음
```

state는 상황을 분류하는 classifier이고, feature는 타입의 특성. 상호 specialization은 의미론적으로 부적절.

**수정**:

```python
spec-07: state → feature* → specialization = DENY (p=80)
spec-08: feature* → state → specialization = DENY (p=80)
```


### 1-D. succession 범위 축소 (High)

**현상**: `succ-01: feature* → feature* via succession` (p=40)이 모든 feature 쌍에
temporal ordering을 허용. `expression → port` 같은 무의미한 succession이 커널에서 통과.

```
expression → port → succession = ALLOWED (succ-01)  ← 의미 없음
port → expression → succession = ALLOWED (succ-01)  ← 의미 없음
```

Succession은 시간적 순서를 나타내므로, 참여자는 behavioral feature(step, action, event)로 제한해야 함.

**수정**: `succ-01`을 제거하거나 priority 낮추고, 구체적 allow로 대체

```python
# succ-01 제거
# succ-02: step → step (p=70) — 유지
# succ-03: action → action (p=70) — 유지
succ-04: event → step* → succession = ALLOW (p=60)   # 신규: event → step/action
succ-05: step* → event → succession = ALLOW (p=60)   # 신규: step/action → event
succ-06: event → event → succession = ALLOW (p=60)   # 신규: event chain
```

**영향**: 기존 프로파일에서 ArchiMate/TOGAF/Zachman의 `succession/triggers` 사용은
모두 `step(Behavior) → step(Behavior)` 또는 `event(Event) → step(Behavior)` 패턴이므로 영향 없음.


### 1-E. 공통 프로파일 패턴 커널 승격 (Medium)

3개 이상 프로파일에서 반복되는 deny 패턴을 커널로 승격:

| 패턴 | 프로파일 출현 | 커널 규칙 |
|------|:---:|------|
| classifier/item cannot trigger | ArchiMate, TOGAF, SysML | `trig-03` 이미 존재 (classifier*→step*) |
| package cannot trigger | TOGAF, SysML | `trig-04` 이미 존재 (package→step*) |
| PassiveStructure(item) → ActiveStructure(structure) composition 금지 | ArchiMate, TOGAF | 신규 `own-05` 필요 |

`trig-03`, `trig-04`는 이미 커널에 존재. 신규 추가:

```python
own-05: item → structure → ownership = DENY (p=80)
  notes: "Item(passive) cannot own Structure(active)"
```


## 2. 엔티티/관계 데이터 모델 개선 (types.py, definition.py)

### 2-A. Effective plays/roles API (High)

**현상**: `KernelSchema`에 엔티티의 상속된 plays나 관계의 상속된 roles를 계산하는 API가 없음.

- `action.plays` → `()` (빈 튜플). 실제로는 `step`에서 `succession:predecessor/successor`, `triggering:responding`을 상속받지만 조회 불가.
- `flow.roles` → `()`. 실제로는 `connector`에서 `source/target`을 상속받지만 조회 불가.

**수정**: `KernelSchema`에 2개 메서드 추가

```python
def effective_plays(self, entity_name: str) -> tuple[str, ...]:
    """엔티티의 plays + 모든 조상의 plays를 합산."""

def effective_roles(self, relation_name: str) -> tuple[KernelRole, ...]:
    """관계의 roles + 부모 관계의 roles를 합산 (자식이 우선)."""
```

### 2-B. KERNEL_METADATA validity_rules 동적화 (Low)

```python
# 현재 (v1.1): 하드코딩
KERNEL_METADATA = {"validity_rules": 50, ...}

# v1.2: spec에서 자동 계산
# definition.py에서는 규칙 수를 선언하지 않고, spec.py에서 계산
```


## 3. 프로파일 시스템 개선 (profile_validator.py)

### 3-A. `#Layer` 패턴 평가 (Low)

`#Layer` 패턴 매칭이 구현되어 있지만 4개 프로파일 모두 미사용.
v1.2에서 제거하지 않고 유지하되, 문서에 "사용 예정" 표시 또는 deprecation 결정.


## 4. 네이밍 개선 (Low)

### 4-A. triggering 역할명 `event` → `trigger_source`

`triggering` 관계의 역할 `event`가 엔티티 `event`와 이름 충돌.
역할은 "이벤트를 발생시키는 쪽"이고 실제로 `feature` 타입이 play하므로
`trigger_source`로 변경하면 혼동 감소.

```python
# v1.1
KernelRole("event", "feature")
# v1.2
KernelRole("trigger_source", "feature")
```

**영향**: TQL 스키마 변경 필요. 기존 프로파일 코드에는 영향 없음 (역할명은 프로파일에서 참조하지 않음).


## 5. 평가 모듈 개선 (evaluation.py)

v1.1에서 도입한 5개 메트릭(type_coverage, relation_coverage, category_homogeneity,
rule_density, deny_compensation_ratio)의 정확성은 검증 완료. v1.2에서 3개 메트릭 추가.

### 5-A. Compensation Hotspot 추적 (High)

**현상**: `deny_compensation_ratio`는 "몇 개가 보상인지"만 측정하고,
"어떤 커널 규칙이 가장 많이 보상되는지"는 추적하지 않음.

v1.2 커널 규칙 강화 우선순위를 데이터 기반으로 결정하려면 hotspot이 필요함.

**수정**: `ProfileMetrics`에 필드 추가 + `ProfileComparison`에 집계

```python
# ProfileMetrics
compensation_hotspots: dict[str, int]
  # 커널 규칙 ID → 해당 규칙을 보상하는 프로파일 deny 수
  # 예: {"assoc-01": 8, "spec-01": 3, "own-01": 2}

# ProfileComparison
cross_profile_hotspots: dict[str, int]
  # 커널 규칙 ID → 보상하는 프로파일 수 (4개 프로파일 중 몇 개가 보상하는지)
  # 예: {"assoc-01": 4, "ftyp-01": 1}  → assoc-01이 최우선 강화 대상
```

**구현**: `_find_compensation_denies()`가 이미 `validate_relationship()`을 호출하므로,
매칭된 커널 규칙 ID(`result.rule_id`)를 수집하면 됨. 반환값을 `list[str]` → `list[tuple[str, str]]`
(profile_deny_id, kernel_rule_id)로 확장.

**활용**: v1.2 커널 규칙 보강 시 hotspot 상위부터 처리하면 프로파일 부담 감소 최대화.

### 5-B. Element Participation Ratio (Medium)

**현상**: ea-metamodel의 ProfileValidator에는 `element_participation_ratio`가 있지만
ea-kernel evaluation에는 없음. "요소 중 몇 %가 최소 1개 validity rule에 참여하는지" 측정.

현재 4개 프로파일은 모두 높은 참여율이지만, 향후 프로파일 추가 시 규칙 누락 검출에 유용.

**수정**: `ProfileMetrics`에 필드 추가

```python
element_participation_ratio: float  # 0.0–1.0
non_participating_elements: tuple[str, ...]
  # 어떤 validity rule에도 source/target으로 등장하지 않는 요소 이름
```

**구현**: `evaluate()` 내에서 모든 explicit rule의 source/target 패턴을
`_matching_elements()`로 확장한 뒤, 전체 elements 대비 참여 비율 계산.
wildcard(`*`) 패턴과 fallback 규칙(priority=1)은 제외.

### 5-C. Compensation Delta (v1.1 → v1.2 비교) (High)

**현상**: v1.2 커널 규칙 강화 후 프로파일의 deny_compensation_ratio가 얼마나 감소하는지
자동 측정하는 방법이 없음. 커널 개선 효과를 정량적으로 입증하려면 before/after 비교 필요.

**수정**: `ProfileEvaluator`에 메서드 추가

```python
def compare_kernels(
    self,
    other: ProfileEvaluator,
    *profiles: KernelProfile,
) -> KernelComparisonResult:
    """두 커널 버전에 대해 동일 프로파일을 평가하고 delta 계산."""
```

```python
@dataclass(frozen=True)
class KernelComparisonResult:
    """커널 버전 간 평가 delta."""
    profiles: tuple[str, ...]
    before: dict[str, ProfileMetrics]   # self(v1.1) 기준
    after: dict[str, ProfileMetrics]    # other(v1.2) 기준
    compensation_delta: dict[str, float]
      # 프로파일별 deny_compensation_ratio 변화량 (음수 = 개선)
    resolved_hotspots: dict[str, tuple[str, ...]]
      # 커널 규칙 ID → 해소된 compensation deny ID 목록
```

**활용**: v1.2 작업 완료 후 `compare_kernels(v11_evaluator, v12_evaluator, *profiles)` 실행하면
"v1.2가 프로파일 부담을 얼마나 줄였는지" 자동 보고.
